Yes — the right way to build this is as a small **data pipeline platform**, not just a scraper, with a static operator UI on GitHub Pages/Jekyll and the ingestion, verification, enrichment, and export logic on Cloudflare Pages/Workers backed by D1 and Queues. GitHub Pages is powered by Jekyll for static hosting, while Cloudflare Workers/Pages can handle AI, SQL, HTML parsing, and async processing; D1 is Cloudflare’s serverless SQL database, Queues can offload scraping jobs, Browser Run can drive headless-browser scraping when needed, and AI Gateway/Workers AI can sit in front of AI verification steps.[1][2][3][4][5][6][7]

## Architecture

Use a **split-stack** setup: Jekyll on GitHub Pages for the dashboard, docs, forms, review screens, and CSV download links, and Cloudflare for the API layer, worker orchestration, scraping, enrichment, verification, and database access. Cloudflare D1 is designed to be queried from Workers and Pages projects, HTMLRewriter can parse and transform HTML inside Workers, and Queues are meant for background delivery and batch processing so scraping does not block user requests.[2][4][5][7]

Suggested flow:
- Static front end: source submission, search presets, review queue, export page.[8][2]
- API worker: accepts search jobs and writes normalized records into D1.[5][9]
- Queue consumer: crawls domains, extracts person/company data, and retries failures.[7]
- AI verifier: scores confidence, checks field consistency, flags bad emails/roles/duplicates, and routes all model traffic through AI Gateway.[3][1]
- Advanced scraper path: use Browser Run only for JavaScript-heavy pages or anti-bot sites.[6]

## Data model

Your requested export columns are a solid MVP, but for angel, VC, and PE use you should keep more internal fields than you export. D1 uses SQL with SQLite semantics, so it fits well for a normalized contacts-plus-companies schema with verification status and source tracking.[5]

Recommended internal schema:
- `contacts`: first_name, last_name, full_name, url, email, company, position, linkedin_url, country, city, investor_type, sector_focus, stage_focus, source_url, confidence_score, verification_status, last_verified_at, notes.
- `organizations`: company_name, website, investor_type, description, geography, sectors, stages, aum_or_fund_size, source_url.
- `sources`: source_url, domain, scraped_at, parser_type, status_code, content_hash.
- `exports`: export_id, filter_json, generated_at, row_count, csv_path.[5]

Export CSV for MVP:

Create a D1 schema for contacts, organizations, source_pages, scrape_jobs, scrape_results, verification_events, and export_runs. ### 3. Scraping engine
Build a Cloudflare Worker scraping service that accepts a target URL or domain and extracts candidate contact data from public pages such as team, about, portfolio, advisors, partners, mentors, contact, and legal pages. First try standard fetch plus HTMLRewriter/DOM parsing for static HTML, then fall back to Browser Run for JavaScript-rendered pages. Capture source URL, extracted text snippet, entity type, and raw confidence score for each lead candidate.[4][6]

### 4. Queue-based job processing
Implement async job processing with Cloudflare Queues so incoming scrape jobs are added to a queue and processed in batches by a consumer Worker. The producer API should return a job ID immediately, and the consumer should update job states such as queued, running, partial, completed, and failed. Add retry handling, dead-letter logic, and per-domain rate limiting.[7]

### 5. AI verification
Add an AI verification module using Workers AI through AI Gateway to validate extracted names, companies, job titles, and email plausibility. The verifier should output confidence_score, verification_status, reasons, and normalized values, and it should reject clearly generic inboxes unless explicitly allowed. Route all model calls through AI Gateway and keep prompts/configs centralized.[10][1][3]

### 6. Lead scoring
Build a scoring engine for investor relevance. Score higher for roles like Partner, Principal, Investor, Scout, Operating Partner, Venture Partner, Platform, Community, Legal Counsel to Funds, Wellness Coach for Founders, Mentor, and Hedge Fund/Family Office decision roles. Also support categories for angel investing, venture capital, and private equity, and add filters for geography, sector focus, and stage focus.[5]

### 7. CSV export
Create a secure CSV export endpoint that outputs exactly these columns: First Name, Last Name, URL, Email Address, Company, Position. Support filters by entity type, confidence score threshold, verification status, domain, geography, and last verified date. Save export metadata to D1 and make the file downloadable from the static dashboard.[2][5]

### 8. Review dashboard
Build the Jekyll operator dashboard for GitHub Pages with pages to submit domains, monitor jobs, review extracted leads, approve/reject records, and trigger CSV exports. The dashboard should call the Cloudflare API, use responsive tables/cards, and clearly show source URL, confidence, verification status, and last updated time.[8][2]

### 9. Source strategy
Implement source-type presets: investors, holding companies, hedge funds, wellness coaches, mentors, and operational partners such as tech, legal, finance, recruiting, and services. Each preset should include seed page patterns, role keywords, exclusion keywords, and extraction rules. Store presets in JSON so new verticals can be added without code changes.[4][5]

### 10. Compliance guardrails
Add compliance controls so the system only collects publicly available business information, respects robots.txt and per-domain throttling where configured, stores source provenance for every field, and requires manual approval before export of low-confidence records. Build an audit log for who created jobs, reviewed records, and exported files.[7][5]

## MVP scope

For the first version, target **public company/team/contact pages only** and avoid trying to scrape every social network immediately, because HTML parsing in Workers is straightforward and reliable, while headless browsing should be the fallback path, not the default. Cloudflare’s HTMLRewriter is well suited for parsing public HTML streams, and Browser Run is better reserved for pages that require real browser automation.[4][6]

A practical MVP definition:
- Input: one domain or a CSV list of domains.
- Output: verified lead CSV with your 6 required columns.
- Sources: public website pages only.
- Verification: AI plus rule-based checks.
- Review: human approval screen before export.[1][5]
