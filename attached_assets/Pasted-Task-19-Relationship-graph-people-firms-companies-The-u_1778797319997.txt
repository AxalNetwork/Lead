Task 19 — Relationship graph (people ↔ firms ↔ companies)
The user wants to see how profiles and companies relate. Build a relationship graph that surfaces co-investment ties, shared employers, board-overlap, school overlap, family-office links, and any other relationship signal we can derive from the data we already collect.
Migration apps/worker/migrations/110_relationships.sql:
CREATE TABLE entities (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  kind TEXT NOT NULL,                 -- 'person','firm','company','school','board'
  ref_table TEXT NOT NULL,            -- 'leads','firms','firm_portfolio'
  ref_id INTEGER NOT NULL,
  display_name TEXT NOT NULL,
  UNIQUE(ref_table, ref_id)
);
CREATE INDEX idx_ent_kind ON entities(kind);
CREATE INDEX idx_ent_name ON entities(display_name);
CREATE TABLE relationships (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  src_entity_id INTEGER NOT NULL,
  dst_entity_id INTEGER NOT NULL,
  kind TEXT NOT NULL,                 -- see list below
  strength REAL DEFAULT 1.0,          -- 0..1
  started_at TEXT,
  ended_at TEXT,
  source TEXT,                        -- 'firm_people','firm_portfolio','sec_form_d','crunchbase','manual','co_investment','school','board','family','referral'
  evidence_url TEXT,
  evidence_json TEXT,
  created_at TEXT DEFAULT (datetime('now')),
  UNIQUE(src_entity_id, dst_entity_id, kind, source)
);
CREATE INDEX idx_rel_src ON relationships(src_entity_id);
CREATE INDEX idx_rel_dst ON relationships(dst_entity_id);
CREATE INDEX idx_rel_kind ON relationships(kind);
Relationship kind values to derive:
works_at — person → firm via firm_people.
was_at — historical employer (when firm_people.ended_at not null or from enrichment employment history).
partner_at — person → firm where firm_people.role matches /partner|gp|principal/i.
founded — person → company.
invested_in — firm → company via firm_portfolio.
led_round_in — firm → company where firm_portfolio.is_lead=1.
co_invested_with — firm ↔ firm when both have a firm_portfolio row with same (company_name, investment_year). Symmetric — write both directions.
board_of — person → company (from public 10-K/DEF 14A filings or manual entry).
school_with — person ↔ person sharing institution + overlapping years (from enrichment education).
colleague_of — person ↔ person sharing a firm in overlapping time ranges.
family_of — manual only (sensitive; gated behind a separate review).
referred — manual; one user pointed us to another lead.
mentions — person → person/company appearing on the same scraped page (weak signal; strength scaled by co-occurrence count).
Build a derivation job (apps/worker/src/scraper/relationships/derive.ts) that scans the source tables and (re-)emits the relationship rows nightly via cron (cron = ["45 3 * * *"]). Idempotent: uses the UNIQUE constraint on (src, dst, kind, source).
Endpoints:
GET /api/relationships/entity/:id?depth=1|2&kinds=...&limit=100 — returns the subgraph rooted at the given entity. Response shape: {nodes:[{id, kind, name, ...}], edges:[{src, dst, kind, strength, source}]}. Use BFS in the worker with a cap on edges returned.
GET /api/relationships/path?src=&dst=&max_hops=4 — shortest-path between two entities. Useful for "do we know anyone at this firm?".
GET /api/relationships/coinvestors/:firmId — firms that co-invested with this firm at least N times.
GET /api/relationships/colleagues/:leadId — every person who worked at any firm this lead worked at, with overlap years.
GET /api/relationships/intros?from=&to= — given the user's email from accessGuard, find the shortest chain of works_at/partner_at/school_with/referred edges from the user (as an entity, auto-created on first call) to to. Returns the chain with each intermediate person's contact channels.
UI: on firm-detail.html and on a new leads/{id}.html page, render a "Relationships" tab with:
A force-directed graph (use d3-force via a small vendored bundle; or hand-roll a Barnes-Hut layout — pick whichever lands under 30KB gzipped). Nodes colored by kind, edges colored by relationship kind, edge thickness by strength.
A "Path to firm" search: pick another firm; we draw the shortest known path.
A "Co-invested with" table.
A "Possible intros" panel suggesting the top 5 people two hops away from a target.
Add a "Relationships" top-level page at apps/site/dashboard/relationships.html with a global search: pick any person or firm, render its subgraph, expand/collapse nodes on click.
Privacy: a relationship of kind='family_of' is hidden from default listings; visible only on the lead detail page and only to allowlisted admin users. Add a relationship_visibility column if you want a more granular gate, but keep it simple — hardcode the family_of filter for now.
Acceptance criteria:
After running the derivation cron, the relationships table has at least works_at, partner_at, invested_in, and co_invested_with rows populated from existing data.
GET /api/relationships/coinvestors/{a16z_firm_id} returns the firms that share portfolio companies with a16z, ordered by overlap count.
GET /api/relationships/intros?to={partner_lead_id} returns a non-empty path when one exists through works_at + school_with edges.
The graph UI on a firm detail page renders ≤ 200 nodes without freezing.
