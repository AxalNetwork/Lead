Task 6 — Enrichment connectors (email, phone, holdings, residency, net-worth signals)
Build an enrichment service that, given a lead with at minimum a name and firm (or a LinkedIn URL), fills in the rich fields from Task 3 by querying multiple data sources in priority order and merging the results.
Create apps/worker/src/enrichment/ with:
providers/hunter.ts — Hunter.io domain-search + email-finder + email verifier. HUNTER_KEY secret.
providers/apollo.ts — Apollo.io people-search + enrich. APOLLO_KEY secret.
providers/rocketreach.ts — RocketReach person lookup. ROCKETREACH_KEY secret.
providers/peopledatalabs.ts — PDL person enrich. PDL_KEY secret.
providers/clearbit_alt.ts — Clearbit was deprecated; use a working alternative like Proxycurl (for LinkedIn data, legally re-sold) with PROXYCURL_KEY.
providers/crunchbase.ts — Crunchbase Basic / Enterprise API. CRUNCHBASE_KEY.
providers/sec_edgar.ts — Form ADV brochures, Form D filings, 13F holdings. No key needed.
providers/opencorporates.ts — director-of, officer-of lookups across 140+ jurisdictions. OPENCORPORATES_KEY.
providers/uk_ch.ts — UK Companies House officers. UK_CH_KEY.
providers/forbes_signals.ts — net-worth tier inferred from public Forbes billionaire / 30-under-30 / Midas List pages (scraped via Task 1's pipeline, cached for 30 days). Surface as net_worth_tier only when confidence ≥ 0.8.
providers/whoisxml.ts — domain WHOIS for inferring residency from personal websites. WHOISXML_KEY.
providers/twitter_oss.ts — public-tweet enrichment via Nitter mirrors (no login, no API key) for headline, bio, location text.
Then merger.ts: takes the union of provider results and emits a single canonical lead diff. Conflict resolution rules:
For each field, pick the value with the highest provider_priority (configurable per field — e.g. emails prefer Hunter, holdings prefer SEC EDGAR).
Email/phone arrays are de-duplicated and union-merged, keeping every source attribution.
Never overwrite a manually-edited field (the lead_history table from Task 3 records change_kind='manual_edit' — check it).
Then orchestrator.ts: enrichLead(leadId, env, opts) -> EnrichmentResult. Caches per-provider responses in KV for 14 days (enrich:{provider}:{key}).
Add endpoints:
POST /api/leads/:id/enrich — runs enrichment now.
POST /api/leads/enrich/bulk — enqueue enrichment for a filtered set.
GET /api/enrichment/providers — returns which providers are configured (based on which secrets are present), so the UI can show which fields are reachable.
Add a scheduled trigger that re-enriches any lead whose last_enriched_at is older than 30 days OR whose priority IN ('p0','p1') and is older than 7 days. Cap at 500 leads per run.
Cost guardrails: each provider has a daily-spend ceiling read from wrangler.toml [vars] (e.g. HUNTER_DAILY_USD=10). Track spend in a new provider_usage table; refuse to call a provider over its ceiling and log block_reason='budget'.
Acceptance criteria:
POST /api/leads/:id/enrich for a seed lead populates emails, phones, socials, country, persona, and at least one financial signal field when at least 3 provider keys are configured.
Each enrichment writes one lead_history row per changed field with the provider name in source.
Hitting a daily budget cap blocks further calls and surfaces in /api/scrapers/health.
